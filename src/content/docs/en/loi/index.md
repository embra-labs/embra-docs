## How to read an error

Every error has three parts:

| Part | Example | Where you see it |
|---|---|---|
| Error code (`reason_code`) | `HEALTHCHECK_FAILED` | The CLI's `--json` output, and the text copied with **"Sao chép diagnostic ID"** (copy diagnostic ID) |
| Vietnamese sentence (`summary_vi`) | "Bản mới không qua readiness trong thời gian khởi động. Bản cũ vẫn phục vụ." | Console and CLI |
| Next step (`next_action`) | `fix_input` | The line under the error in the console, the `bước tiếp:` (next step) line in the CLI |

| `next_action` | Console shows | CLI shows | Meaning |
|---|---|---|---|
| `fix_input` | "Kiểm tra và sửa thông tin." | `sửa đầu vào rồi chạy lại` | Fix your code, config or input and try again |
| `rerun_plan` | "Tạo plan mới để kiểm tra lại." | `chạy lại plan` | The old plan no longer holds; create a new one |
| `owner_review` | "Cần owner hoặc admin xem và quyết định." | `chủ workspace cần xem và duyệt` | An Owner or Admin needs to approve or upgrade |
| `wait` | "Đang xử lý, vui lòng chờ." | `chờ rồi kiểm tra lại` | Wait a moment and try again |
| `contact_operator` | "Cần đội Embra kiểm tra trước khi tiếp tục." | `liên hệ người vận hành` | The Embra team needs to look. See [When to contact us](#when-to-contact-us) |
| `none` | | `không cần làm gì thêm` | No error |

The **"Nội dung từ app — không do Embra viết"** block (content from your app, not written by Embra) under an error is text taken from your app or repo: the tail of the build log, your app's response to the health check, a Postgres error, the DNS records Embra read. The real cause is often here.

## How to find a code

- `Ctrl+F` (`Cmd+F` on a Mac), then type the error code, for example `BUILD_FAILED`.
- Console only shows the Vietnamese sentence? Type its first few words: each entry below lists the sentences you usually see.
- Each code has its own URL: `docs.embra.cloud/en/loi/#<code in lowercase>`, for example `/en/loi/#healthcheck_failed`.

## When to contact us

Email **hello@embra.cloud** with:

1. The **operation ID** (`operation_id`): the `operation:` line in the CLI, or the text copied with **"Sao chép diagnostic ID"** in the console.
2. The **workspace**, project and environment (for example `shop/production`).
3. The **time** of the error, saying whether it is Vietnam time or UTC.
4. The error code and sentence, if you have them.

When an error needs the Embra team (`contact_operator`), the console has a **"Liên hệ hỗ trợ"** (contact support) button that opens an email draft with the operation ID and error code filled in. The draft only holds identifiers, never secrets or your data.

## Build and deploy

### `BUILD_FAILED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 200 | No | `fix_input` | `10` | Fix as described here, then retry |

<!-- /reason-meta -->

Embra could not build an image from your code. The running app is not affected.

If the sentence starts with `embra.toml:`, see [`REPO_CONFIG_INVALID`](#repo_config_invalid). Other sentences:

| Error sentence | Meaning |
|---|---|
| `buildctl lỗi: exit …` or `build trong VM không thành công.` | The build command (Dockerfile or Railpack) failed. The cause is in the build log |
| `railpack prepare lỗi: exit …` | Railpack's repo analysis failed. The reason is in the build log |
| `git fetch lỗi: …`, `git checkout lỗi: …` | Embra could not fetch the commit from GitHub |
| `không thấy Dockerfile.` | `embra.toml` sets `builder = "dockerfile"` but there is no file at that path |
| `root không tồn tại.`, `root không phải thư mục.`, `root trỏ ra ngoài repo.` | `root` in `embra.toml`, or the **Root directory**, is wrong |
| `Image build ra vượt giới hạn dung lượng của gói.` | The image is larger than your plan's disk space |
| `… file migration không hợp lệ.`, `migration trùng tên.`, `quá 100 file migration.`, `migration … vượt … byte.` | Something is wrong in the migrations folder. See [Writing migrations](/en/huong-dan/database-va-migration/#writing-migrations) |
| `preview.seed không tồn tại.` | The file set in `[preview] seed` is not in the repo |
| `Upload của build này không còn tồn tại. Upload lại rồi build.` | The upload from `embra deploy` has expired |

**How to fix it:**

1. Click **"Xem build logs"** (view build logs) and read from the bottom up. The first error from npm, pip, go or docker is usually the cause.
2. Run the same build command on your machine. With a `Dockerfile`, run `docker build .` at the repo root (or in `root`).
3. Log shows `egress từ chối "<host>"` (egress denied): the build needs a host that is not open yet. Email that host name to hello@embra.cloud. Open hosts: [How Embra builds your app](/en/huong-dan/chuan-bi-app/#how-embra-builds-your-app).
4. Image too large: use a multi-stage Dockerfile that copies only the build output (for example `dist/`) into the last stage, install production dependencies only (`npm ci --omit=dev`), add a `.dockerignore` that drops `node_modules`, `.git` and test files.
5. `builder = "dockerfile"` without a Dockerfile: remove the `builder` line so Embra picks Railpack, or fix `dockerfile` to the right path, relative to `root`.
6. Commit and push again.

<details>
<summary>Sample multi-stage Dockerfile for a Node app</summary>

```dockerfile
# Ví dụ Dockerfile nhiều stage cho app Node
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
CMD ["node", "dist/main.js"]
```

</details>

**Data safe?** Yes. A failed build deploys nothing and does not touch the database.

**Retry?** The same commit usually fails the same way. `không khởi động được VM.`, `VM tắt trước khi sẵn sàng.` and `mất kết nối với embra-buildd giữa chừng build.` are on Embra's side: click **"Build lại"** (rebuild) once.

**Contact us when:** an Embra-side error repeats after a rebuild, or the build works on your machine but fails on Embra and the log does not show why.

### `BUILD_TIMEOUT`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 200 | No | `fix_input` | `10` | Fix as described here, then retry |

<!-- /reason-meta -->

The build ran too long and was stopped. Sentence: `build vượt thời gian cho phép.` The build time limit depends on your plan and is never more than 25 minutes. The running app is not affected.

| Cause | Fix |
|---|---|
| Installing dependencies without a lockfile, so the whole tree is resolved again | Commit your lockfile (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`…) |
| Tests, lint or large downloads inside the build | Move tests and lint to CI |
| A Dockerfile step waits on a host that is not open until time runs out (log shows `egress từ chối`) | Email the host name to hello@embra.cloud |
| The Dockerfile copies all code before installing dependencies, so every change reinstalls | Copy the dependency manifest and install first, code after (sample below) |

```dockerfile
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
```

Open **"Xem build logs"** to see where the build stopped, fix it and push again.

**Data safe?** Yes. Nothing is deployed.

**Contact us when:** the build stops while downloading from a host that is open, or it takes under 25 minutes on your machine but still times out on Embra.

### `HEALTHCHECK_FAILED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 200 | No | `fix_input` | `10` | Fix as described here, then retry |

<!-- /reason-meta -->

The new version started but did not answer the health check correctly, so Embra did not move traffic to it (or moved traffic back to the old version).

| Error sentence | App right now |
|---|---|
| `Bản mới không qua readiness trong thời gian khởi động. Bản cũ vẫn phục vụ.` | The old version keeps running. On a first deploy, nothing is running yet |
| `Bản mới lỗi sau khi nhận traffic, route đã được trả về bản cũ.` | The new version failed during the 30-second watch; traffic is back on the old version |
| `App không qua readiness sau khi chạy lại; app vẫn đang tạm dừng.` | You turned a paused app back on but it did not come up; the app stays off |
| `App không chạy được trên bản khôi phục (không qua readiness). …` | The restore was cancelled; the old app and database keep running |
| `Deploy đã xong nhưng app chưa trả lời kiểm tra sức khoẻ sau 2 phút. …` (CLI) | `embra deploy` waited 2 minutes and the app is not healthy yet. Check the app log |

Embra sends a `GET` to `health_path` every 2 seconds and needs **3 consecutive 2xx responses** within `startup_grace_seconds` (60 seconds by default). Details: [Health check](/en/huong-dan/chuan-bi-app/#health-check).

| Cause | Fix |
|---|---|
| The app listens on `127.0.0.1` or `localhost`, unreachable from outside the container | Listen on `0.0.0.0` (framework samples below) |
| The app listens on a port other than `[deploy] port` (3000 by default), such as the framework default (8000, 8080, 5173) | Read the port from the `PORT` env var. Embra sets `PORT` to `[deploy] port` unless you set a `PORT` secret yourself |
| `health_path` returns 3xx: a redirect to login, to HTTPS or to add a trailing `/`. Redirects do not count as passing | Add a dedicated route, for example `/healthz`, returning 2xx with no login and no redirect |
| `health_path` returns 4xx: the path does not exist, needs login, or the framework blocks an unknown `Host` header. Embra calls the container's internal IP directly, so `Host` is `IP:port`, not your domain | As above; for Django see the middleware sample below |
| The app crashes on startup: missing secret, no database connection, migrations on startup (the app's database user cannot change the schema) | Read the app log. Remove startup migrations (`prisma migrate deploy`, TypeORM `synchronize: true`…): migrations go through Embra, see [Database and migrations](/en/huong-dan/database-va-migration/) |
| The app takes longer to start than `startup_grace_seconds` | Raise `startup_grace_seconds` (at most 300) |

**How to fix it:**

1. Open **"Logs"** and read the app log around the failed deploy. Startup crashes show up clearly here.
2. Read the **"Nội dung từ app — không do Embra viết"** block: your app's response to the last health check.
3. Fix per the table above and set the health route in `embra.toml`:

   ```toml
   [deploy]
   health_path = "/healthz"
   ```

4. Push again.

<details>
<summary>Listening on <code>0.0.0.0:$PORT</code> per framework</summary>

**Express:**

```js
const port = Number(process.env.PORT) || 3000;
app.get('/healthz', (req, res) => res.send('ok'));
app.listen(port, '0.0.0.0');
```

**NestJS** (`src/main.ts`):

```ts
await app.listen(Number(process.env.PORT) || 3000, '0.0.0.0');
```

**Next.js** (`package.json`):

```json
{
  "scripts": {
    "start": "next start -H 0.0.0.0 -p ${PORT:-3000}"
  }
}
```

With `output: 'standalone'` and `node server.js` in a Dockerfile, also set `HOSTNAME`:

```dockerfile
ENV HOSTNAME=0.0.0.0
CMD ["node", "server.js"]
```

**Django** (gunicorn, in a Dockerfile):

```dockerfile
CMD gunicorn myproject.wsgi --bind 0.0.0.0:${PORT:-3000}
```

Django returns 400 when `Host` is not in `ALLOWED_HOSTS`, and may redirect to HTTPS when `SECURE_SSL_REDIRECT` is on. Give the health check its own middleware, placed **first** in `MIDDLEWARE`:

```python
# myproject/health.py
from django.http import HttpResponse


class HealthCheckMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.path == "/healthz":
            return HttpResponse("ok")
        return self.get_response(request)
```

```python
# settings.py
MIDDLEWARE = [
    "myproject.health.HealthCheckMiddleware",
    # ... các middleware còn lại
]
```

**Laravel** (in a Dockerfile):

```dockerfile
CMD php artisan serve --host=0.0.0.0 --port=${PORT:-3000}
```

</details>

:::caution[`$PORT` in array form]
`CMD ["node", "server.js"]` and `start = ["node", "dist/main.js"]` in `embra.toml` are array forms that skip the shell, so a `$PORT` written there is **not** replaced with its value. Read `PORT` in your code, or wrap it in a shell: `CMD ["sh", "-c", "gunicorn myproject.wsgi --bind 0.0.0.0:$PORT"]`.
:::

**Data safe?** It depends:

- **The new version did not pass the health check:** no real traffic reached it. But it did run its startup code with `DATABASE_URL`, so anything that code wrote (for example a seed on startup) stays.
- **The new version failed after receiving traffic:** it served real requests while being watched. Data written then stays in the database.
- **In every case:** if the plan had migrations, **migrations that ran stay applied**, and the old version is running on the new schema. Don't edit an applied migration to "undo" it, or Embra reports [`MIGRATION_HISTORY_CHANGED`](#migration_history_changed). To change the schema back, add a new migration file.

**Retry?** Not without changing something: the health check will fail the same way.

**Contact us when:** the app listens on `0.0.0.0:$PORT` and returns 2xx on `health_path` when run with Docker on your machine, but Embra still reports this error.

### `REPO_CONFIG_INVALID`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 400 | No | `fix_input` | `2` | Fix as described here, then retry |

<!-- /reason-meta -->

Your `embra.toml` has an error. The sentence always starts with `embra.toml:` and names the wrong field. Found during a build, it shows as [`BUILD_FAILED`](#build_failed) with the same sentence.

| Error sentence (examples) | How to fix it |
|---|---|
| `embra.toml: field lạ deploy.prot.` | Fix the field name (here, `port`). Embra does not ignore unknown fields |
| `embra.toml: field deploy.port sai kiểu giá trị.` | Fix the type: `port = 3000`, not `port = "3000"` |
| `embra.toml: sai cú pháp TOML ở dòng 12.` | Fix the syntax on that line (missing quote, missing `]`…) |
| `embra.toml: build.builder phải là "railpack" hoặc "dockerfile".` | Fix the value, or remove the line so Embra picks one |
| `embra.toml: deploy.startup_grace_seconds phải > 0.` | Use 5 to 300 seconds |
| `embra.toml: … phải là đường dẫn tương đối trong repo.`, `… không được trỏ ra ngoài repo.` | Path from the repo root (or from `root`), no leading `/`, no `..` leaving the repo |
| `embra.toml: build.env.EMBRA_…: tiền tố EMBRA_ dành riêng cho Embra.` | Rename the variable |
| `embra.toml: cron.<tên>.schedule: …` | 5-field cron, in UTC, at least 5 minutes apart |
| `embra.toml: file vượt 65536 byte.` | Shorten the file to at most 64 KiB |

Compare with the [`embra.toml` reference](/en/huong-dan/chuan-bi-app/#embratoml). Check the syntax locally, for example `python3 -c "import tomllib; tomllib.load(open('embra.toml','rb'))"`, then commit and push again.

**Data safe?** Yes. Nothing is deployed.

### `SOURCE_NOT_CONNECTED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 409 | No | `fix_input` | `10` | Fix as described here, then retry |

<!-- /reason-meta -->

Embra cannot read this environment's GitHub repo.

**Sentences:**

- `Environment chưa nối với repo GitHub. …`
- `Environment không còn nối với repo GitHub.`
- `GitHub installation đã bị gỡ hoặc tạm dừng.`
- `Không lấy được quyền đọc repo: installation đã bị gỡ, tạm dừng hoặc mất quyền truy cập repo.`
- `Không đọc được nhánh đã nối: repo, nhánh hoặc installation không còn truy cập được.`
- `Hãy đăng nhập bằng GitHub trước khi kết nối repo.`

**Common causes:**

- The Embra GitHub App was uninstalled or suspended on the account or organization.
- When installing the GitHub App you chose "Only select repositories" and this repo is not in it (or was just removed).
- The repo was renamed, transferred or deleted. The linked branch was renamed or deleted.
- You signed in to Embra with Google. Only people signed in with GitHub can link a repo.

**How to fix it:**

1. Open **Cài đặt → "Source code"** (settings → source code) → **"Cài / cập nhật quyền GitHub App"** (install / update GitHub App permissions).
2. Grant access to the repo on GitHub again.
3. Check the repo and branch names are still right. Branch renamed? Link the new one.
4. Click **"Build lại"** (rebuild).

See also [Deploy from GitHub](/en/huong-dan/deploy-tu-github/#creating-the-app).

**Data safe?** Yes. The running app keeps running; Embra just cannot build a new version.

## Database and migrations

Migration sentences sometimes give the statement's "lớp" (class). Match it to [How Embra checks migrations](/en/huong-dan/database-va-migration/#how-embra-checks-migrations):

| Class | Group |
|---|---|
| A | Safe |
| B | Changes or deletes data |
| C | Long table lock |
| D | Cannot run in a transaction |
| E, F | Not supported (E: Embra cannot parse the statement; F: forbidden) |

### `MIGRATION_UNSUPPORTED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 422 | No | `fix_input` | `10` | Remove the class E/F statement, push again |

<!-- /reason-meta -->

A statement in a migration file is of a kind Embra cannot run yet, so the plan is refused before the database is touched. After a successful build, the console shows **"Build xong · cần sửa config"** (build done, fix config) and **"Không tạo được plan deploy"** (could not create a deploy plan).

**Sentences:**

- `File 0003_x.sql, câu lệnh #2 (CreateFunctionStmt) lớp E: …` or `… lớp F: …`
- `File 0003_x.sql: không đọc được SQL nên không thể chứng minh an toàn.`
- `File 0004_x.sql, câu lệnh #1 (IndexStmt) lớp D: … lệnh không chạy trong transaction (như CREATE INDEX CONCURRENTLY) phải ở file riêng, chỉ có đúng một câu lệnh`
- `SQL của migration đã thay đổi bảng nội bộ của Embra. Đã rollback; không được phép.`
- `Migration không hợp lệ để chạy trên production.`

| Cause | Fix |
|---|---|
| The file has a function, procedure, trigger, view, `DO` block, `CREATE EXTENSION`, `CREATE SCHEMA`, `GRANT`/`REVOKE` or `COPY` (common in ORM-generated migrations) | Move that logic into app code. Embra cannot run these yet |
| The file has `BEGIN`/`COMMIT` | Remove them. Embra wraps each file in a transaction itself |
| `CREATE INDEX CONCURRENTLY` shares a file with other statements | Move it to its own file, with only that statement |
| SQL for another database (MySQL, SQLite) or Postgres syntax Embra cannot parse | Rewrite it as Postgres SQL |

Find the statement by its `#` number (counting from 1) in the file the sentence names; the original statement is in the **"Nội dung từ app — không do Embra viết"** block. The file never ran, so edit it directly, then commit and push again.

**Data safe?** Yes. Embra refuses at the planning step. Only `SQL của migration đã thay đổi bảng nội bộ của Embra.` happens while running, and Embra rolled that statement back.

### `MIGRATION_REHEARSAL_FAILED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 200 | No | `fix_input` | `10` | Fix the SQL, check with `embra plan`, then push |

<!-- /reason-meta -->

A migration failed:

| Error sentence | Where it failed |
|---|---|
| `Diễn tập migration thất bại trên bản sao dữ liệu; chưa đụng production. …` | On a copy of your data. Production was not touched |
| `Migration lỗi trên production dù đã diễn tập thành công: production khác bản sao. Câu lệnh lỗi đã rollback.` | On production. The failing statement was rolled back |

The Postgres error (for example `column "status" of relation "orders" contains null values`) is in the **"Nội dung từ app — không do Embra viết"** block, with the failing file and statement.

**Common causes:**

- Adding a `NOT NULL` column without a `DEFAULT` to a table that has rows.
- Creating a `UNIQUE` constraint or foreign key that existing data violates (duplicates, references to missing rows).
- Changing a column type when old data cannot be converted (for example text to number).
- Referencing a table or column that does not exist yet, because of file order.
- A migration that works on an empty local database but fails with real data.

**How to fix it:** change the SQL so it works with the existing data. For example, add a required column in three steps:

```sql
ALTER TABLE orders ADD COLUMN status text;
UPDATE orders SET status = 'paid' WHERE status IS NULL;
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
```

Or shorter: `ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'paid';`

## When Embra stops to check

The three codes below share one rule: when Embra is **not sure** a step finished, it **stops on purpose** instead of retrying. Retrying something with an unknown outcome, such as running a migration twice or switching databases without knowing their state, can damage data. The Embra team checks the real state before reopening the environment.

### `RECOVERY_REQUIRED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 200 | No | `contact_operator` | `30` | None, on purpose. Email hello@embra.cloud with the `operation_id` |

<!-- /reason-meta -->

An operation on the environment (deploy, rollback, restore, app on/off…) ended without Embra knowing the outcome, for example because the connection to the server dropped midway. The console shows **"Cần đội Embra hỗ trợ"** (needs Embra team support), and the overview shows **"Đội Embra cần kiểm tra trước khi bạn deploy tiếp"** (the Embra team needs to check before you deploy again).

**State right now:**

- Embra keeps traffic as it was at the incident. Depending on timing, the app may be running normally, running the new version, or stopped (for example during a switch to a restored database).
- The environment is blocked: deploys, builds on push, rollback, restore, app on/off, domain changes and data imports are refused with [`ENVIRONMENT_BLOCKED`](#environment_blocked).
- Cron jobs don't run. Scheduled backups are paused.

**Do NOT:**

- **Delete the environment.** Still allowed, but it also deletes the database and backups the Embra team needs to check and recover.
- Run SQL yourself to "fix" the schema or data: it makes checking harder.
- Keep pushing or revoke secrets to "unblock" it: no effect.

**Do:**

1. Click **"Liên hệ hỗ trợ"** (contact support) in the console, or email hello@embra.cloud with the operation ID, workspace, environment and time.
2. Note what you did just before the error appeared.
3. If the app is failing for your users, say so in the email so the team can prioritize.

### `MIGRATION_UNKNOWN`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 200 | No | `contact_operator` | `30` | None, on purpose. Email hello@embra.cloud with the `operation_id` |

<!-- /reason-meta -->

Embra lost contact while running a migration on production, so it does not know whether the migration was applied. The console shows **"Cần xác minh dữ liệu"** (data needs verifying).

**State right now:**

- **The old code keeps running.** The new app has not started, because Embra only starts it after migrations finish.
- The schema may be old or new. Each migration file runs in its own transaction, so a file is either fully applied or not at all (except a `CREATE INDEX CONCURRENTLY` file, which does not run in a transaction).
- Embra took a database snapshot right before running the migration.
- The environment is blocked as with [`RECOVERY_REQUIRED`](#recovery_required).

**Do NOT:**

- Delete the environment or the database.
- Edit, rename or delete the pending migration files, or add a new migration to "run it again".
- Re-run the migration statements by hand.

**Do:** email hello@embra.cloud with the operation ID, workspace, environment and time. The Embra team checks the real schema, records the right outcome and reopens the environment.

### `ENVIRONMENT_BLOCKED`

<!-- reason-meta: generated by scripts/reasons.mjs, do not edit -->

| HTTP | Auto retry | `next_action` | Exit code | Next step |
|---|---|---|---|---|
| 409 | No | `contact_operator` | `30` | None, on purpose. Email hello@embra.cloud with the `operation_id` |

<!-- /reason-meta -->

The environment is blocked after an incident with an unknown outcome ([`RECOVERY_REQUIRED`](#recovery_required) or [`MIGRATION_UNKNOWN`](#migration_unknown)). Every change is refused until the Embra team has checked, including approving a pending deploy or import plan. The plan stays awaiting approval: once unblocked you can approve it again (if it has not expired). **"Từ chối"** (reject) still works. The overview shows **"Đội Embra cần kiểm tra trước khi bạn deploy tiếp"**, and the service shows **"Chờ đội Embra kiểm tra"** (waiting for the Embra team to check).

Sentence: `Environment đang bị chặn sau một sự cố chưa rõ kết quả. Liên hệ đội Embra (hello@embra.cloud).`

**Retry?** No. It is refused the same way until the environment is reopened.

**Do NOT** delete the environment. Email hello@embra.cloud with the operation ID of the first failed operation (the one marked **"Cần đội Embra hỗ trợ"** or **"Cần xác minh dữ liệu"** under **"Lần deploy"** (deploys)), the workspace, environment and time.

The sentence `Database không ở trạng thái sẵn sàng (…). Liên hệ đội Embra (hello@embra.cloud).` uses this code too: the environment's database is in a failed state. Handle it the same way.

## CLI exit codes

Use exit codes so CI scripts know what to do:

| Exit code | Meaning |
|---|---|
| `0` | Done |
| `1` | Sign-in error, not found, cannot connect (`API_UNREACHABLE`), or an error on Embra's side |
| `2` | Invalid input (`INVALID_INPUT`, `REPO_CONFIG_INVALID`, `SOURCE_ARCHIVE_INVALID`) |
| `10` | The action was refused or failed (most error codes) |
| `20` | Waiting for approval (`APPROVAL_REQUIRED`, `MIGRATION_DATA_LOSS`) |
| `30` | Needs the Embra team (`RECOVERY_REQUIRED`, `MIGRATION_UNKNOWN`, `ENVIRONMENT_BLOCKED`, suspensions) |
| `75` | Temporary, try again later (`RATE_LIMITED`, `TEMPORARILY_UNAVAILABLE`), or the wait ran out (`WAIT_TIMEOUT`) |
